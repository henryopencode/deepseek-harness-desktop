# Agent Note: 有界的 Web 运行时更新安装

Status: implemented

[English](2026-09-01-web-runtime-update-install-wait.md) | 中文

## Problem

受管 Web 更新器会先安装依赖，并可能编译本地 Whisper 可执行文件，然后才停止和重启服务。浏览器立即收到“已接受”响应，却把 15 秒轮询上限当成重启失败，实际安装可能仍在进行。没有截止时间的下载请求也可能在发布源停止响应时无限持有生命周期锁。

## Decision

更新器对发布元数据、归档和校验文件请求统一使用经过校验的网络超时。`update-config.json` 可以设置 `networkTimeoutMs`，`DSH_UPDATE_NETWORK_TIMEOUT_MS` 可在部署中覆盖它；默认值为五分钟。超时请求会中止响应体，并在释放生命周期锁前报告操作和持续时间。

浏览器以一秒间隔最多等待十分钟，持续调用 `host.describe` 直到它报告目标版本，覆盖下载、依赖安装、Whisper 编译和重启。进行中的提示会说明安装工作，并提醒首次更新可能需要数分钟。达到上限时，提示会说明更新可能仍在进行，并保留提示供稍后刷新，而不是声称服务重启失败。

## Verification

更新器测试覆盖 SemVer 和校验和行为，并验证无响应 HTTP 下载会中止且给出有界诊断。浏览器测试覆盖延长后的默认轮询预算，并保留重试、忽略、远程能力和成功刷新行为。

## Alternatives considered

**保持 15 秒的浏览器上限。** 这会把正常的首次安装显示为失败，并让用户在更新器可能仍持有生命周期锁时重复尝试。

**不设置截止时间地等待。** 这会隐藏永久卡住的发布连接，并可能无限持有生命周期锁；经过校验的上限让失败可恢复且可诊断。

**通过 Host API 暴露安装进度。** 这会为 detached 更新器增加第二套进度协议，而其持久结果只是活动版本。有界等待和版本轮询已经覆盖所需生命周期，不需要增加模型或会话可见状态。

## Consequences

首次更新期间，浏览器可能在准备受管运行时的数分钟内保持忙碌。缓慢或卡住的网络请求现在会在配置上限内终止，而超过浏览器等待窗口的安装会被描述为仍在进行而非失败。运维人员可以按运行包调整网络上限，无需改变浏览器安装等待预算。
